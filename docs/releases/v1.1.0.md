# v1.1.0 — saves that fit, and files that are kept

This release is almost entirely about saves.

**Fixed: large saves are no longer cut off.** The Pocket's save slot holds
just under 64 KB. Some games save into a 64 KB flash block, and in 1.0.x
those saves did not fit: Biomotor Unitron 2, Faselei!, Neo Turf Masters,
Neo 21 and Bust-A-Move lost part of every save. Saves now use a new
format (V4) that packs runs of erased flash, so they fit whole. Unitron 2's
72 KB takes under 4 KB. Saves from 1.0.x load as before and are rewritten
in the new format the next time the game saves. A 1.0.x save that was already
cut off can only give back what it holds: the rest was never written to the
card. *(The packed format and the double-banked staging behind it are
@supergarbo's design from #5.)*

**Fixed: a save file the core refuses is never overwritten.** Examples
are a damaged file, a file in a format this build does not know, or a save
that belongs to a different dump of the ROM. The core now leaves such a file
on the card byte for byte and does not save for the rest of that session.
1.0.2 refused such files too, but then went on saving: whatever the game
wrote next, starting from no save at all, went over the file. We reproduced
this on hardware: 1.0.2, given a save written by a newer test build, turned
it into a file that matches the one attached to #3 in every header word. We
don't know yet whether this is exactly what happened there, but it produces
the same file. *(Thank you, @pomettini, for reporting it again and attaching
the file. Without it there would have been nothing to check the reproduction
against.)*

There is no on-screen message when this happens. The game simply starts as
if it had no save. See [If a game starts without its save](#if-a-game-starts-without-its-save)
below.

**Found during release testing: a launch that does not recognise its own
save.** Rarely, the core works out the wrong checksum for a game at launch,
although the Pocket delivers the game intact. A save is bound to its ROM's
checksum, so the core then takes the save for another ROM's and refuses it:
it keeps the file as it is and saves nothing in that session. You see the
game without its save, and the next launch brings it back. We saw this
seven times with Card Fighters' Clash, after quick quit-and-relaunch
cycles, on some test builds. The cause is not known yet, and whether it
shows up depends on the build. The release build went through more than 50
such launches without it, while a build known to show it did show it in the
same session. In 1.0.2 the same misread would have been followed by saving
over the file (with the wrong checksum), and the next normal launch would
then have turned it into exactly the empty file attached to #3. So this is
a second way #3 could have happened; it is not proven that it did. Either
way, 1.1.0 keeps the file.

**New: a damaged save is refused before it reaches the cartridge.** Every
save now carries a checksum over its contents. The core checks it first and
writes to the cartridge only if it matches. A damaged file is refused whole
and stays on the card untouched.

**Fixed: savestates and sleep are safer.**
- Loading a Memory, or waking from sleep, restores the game and its save
  together or not at all. The game is never put back over a save that could
  not be restored.
- Loading a Memory right after the game had saved could hang. It no longer
  does.
- A savestate whose transfer did not complete is rejected instead of loaded.
- A wake that fails no longer costs the save.
- A session where saving is off (a file the core refused) can still sleep
  and wake.
- A Memory or a sleep made in the very first moment of a game that has no
  save yet holds no save of that game. It still loads, unless the game has
  saved in between (see Known limitations).
- Quitting right after loading a Memory can no longer write a save file
  that mixes the old save with the Memory's.

**Fixed: Language and Mono Palette now wait for your settings.** The core
wrote these settings into the BIOS as soon as the BIOS started. If the
Pocket had not handed over your saved settings by then, the game got the
defaults for the whole session: English, even with Japanese selected. (Reset
to BIOS does that step again later, which is why the BIOS menu could show
Japanese while the game did not.) The core now waits for the Pocket's settings before it
starts the game. This fixes #6: in our test, Metal Slug 2nd Mission now
starts in Japanese from a fresh launch. The timing of the
handover comes from the Pocket, so if the language still doesn't follow the
setting on yours, please say so in #6.

Games read these settings when they start. A change made while a game is
running takes effect the next time you launch the game. MiSTer behaves the
same way. Sleep and Memories keep the language the session had.

**New: `tools/savinfo.py` tells you more.** It now also reports which build
wrote a save, whether the last restore came from the file or from a
savestate, and, if a restore was refused, which check refused it. It also
reads sleep states and Memories (`.sta` files): which cartridge a state
belongs to, the save it carries, and, for states made with 1.1.0, how the
last Memory load or wake of that session went.

## If a game starts without its save

The save is almost certainly still on the card, and 1.1.0 does not
overwrite it. Don't overwrite or delete it yourself:

1. **Quit the core.** Don't play on: nothing in that session is saved.
   To help find the cause, make a Memory before you quit: it records the
   checksum the core worked out. Keep it only for the report; don't play
   from it later.
2. *Optional:* copy the save to your computer. It is under `Saves/ngpc/`,
   in the same folders as the game under `Assets/ngpc/` (for example
   `Saves/ngpc/common/<game>.sav`). If you can, open an issue and attach
   it, and the Memory if you made one.
3. **Launch the game again.** If it is the fault described above, the save
   is back.

If it still isn't there, the file is kept all the same; see
[Reporting a problem](#reporting-a-problem). More in
[docs/KNOWN_BEHAVIORS.md](https://github.com/janisc/openfpga-NGPC/blob/main/docs/KNOWN_BEHAVIORS.md).

## Going back to 1.0.x

**Please don't go back to 1.0.x without restoring a backup.** 1.0.x cannot
read the new save format, and a version that is already out can't be taught
to. Given a 1.1.0 save, 1.0.x refuses it and can then save over it, which
is exactly what we reproduced above. Memories made with 1.1.0
carry the new format as well.

- Back up `Saves/ngpc/` before updating.
- If you need to go back to 1.0.2, put back the backup you made before
  updating. Progress made on 1.1.0 stays with 1.1.0.
- If you tried a test build, an updater that goes by version numbers (Pocket
  Sync, for example) may have offered you 1.0.2. Please install 1.1.0
  instead. Saves from the 1.1.0-rc3 test build are read as they are.
- Saves from the PR #5 test build (tagged V3) use a different layout. 1.1.0
  does not read them and leaves them untouched on the card. Restore the
  backup you made before trying that build, or move the file away to start
  fresh.

## Under the hood

- **Save engine.** Staging is double-banked: a save is built in the spare
  bank and published only when it is complete. The V4 format packs erased
  runs and carries a CRC32. The core decodes a file once with flash writes
  held off, and writes for real only if the checksum agrees. The block list
  comes from the file and is committed only when the file is accepted.
  Whether a save holds data is now judged by the image that will be written,
  not by everything the session touched: in 1.0.2 a game that wrote into a
  block and erased it again could still let an empty image claim the slot.
- **Fail closed.** A refused save file freezes saving for the session. The
  committed bank stays exactly as delivered and the core makes no claim on
  the save slot, so the Pocket writes the file back unchanged. The freeze
  travels inside savestates (identity layout 3, which 1.0.2 and rc3 reject
  cleanly). A failed wake freezes too, and an accepted file lifts the
  freeze. A state image that carries another cartridge's CRC counts as "no
  image".
- **States with no image.** A sleep or Memory taken before a save-less
  session's first completed flash operation still holds an earlier
  session's leftover image, which counts as "no image". Such a state loads
  when nothing is dirty, and also while the session holds no save of its
  own and has only erased flash (the BIOS power-up routine erases the
  cartridge's top block at every launch). Any program since the last publish keeps the refusal.
  The engine tells a program from an erase by how long the core's flash
  model stays busy: about 17 clocks for a program, at least 307,200 for an
  erase.
- **No publish at a bad moment:** not while a flash chip is busy, not while
  the Pocket is transferring or reading the save, not while a savestate's
  save is being copied in, and not while a late delivery waits to be
  applied. The committed image survives Reset, and deliveries are
  tracked across cartridge reloads.
- **Savestates.** State requests are queued, with an explicit done/reject
  handshake. The copier starts draining only after the stager has parked
  (this was the hang), with a ~2 s timeout. The bridge loads only a
  transfer that reached its last word. A cartridge reload answers a pending
  state apply as refused. The staging arbiter can no longer drop a
  one-cycle request.
- **Load timing.** A Memory load, or a wake that arrives after start-up,
  waits until both flash chips are idle before it holds the machine. An
  erase or program in flight then finishes and is recorded, instead of being
  cut in half unseen. (A save the game makes of several operations can
  still be cut between them, as a reset at that moment would cut it.) The
  commit at the end of an accepted load waits while the Pocket reads the
  save slot, so a flush can no longer straddle it and write a file of two
  images. An accepted load can take up to ~10 ms longer.
- **Staging port.** A Pocket read of the save slot now waits until the
  staging memory's request slot is empty, so it can no longer displace a
  queued write. A Pocket save write and a savestate copy write in the same
  clock now take turns: the Pocket's goes first, and the copy's is replayed
  one clock later. Before, the Pocket's write was lost. The copy is held to
  a shallow queue, so the Pocket's writes, which cannot wait, always find
  room.
- **Settings.** The BIOS setup waits for the Pocket's Reset Exit, with a
  ~2.7 s fallback counted in BIOS standby. A savestate restore cancels the
  automatic game start if it was still pending.
- **Diagnostics.** Every save header records how much of the save came in
  from a savestate rather than from the file, the writer revision (0x06 for
  1.1.0), and a verdict for every restore outcome together with the header
  field that failed. One more flag marks a save-engine write to staging
  while a savestate's save was being copied in. No logic in the core does
  that, so it should never be set. Every sleep state and Memory now carries
  a load stamp: the number of loads since the core started or was last reset,
  and for the last one, which identity checks passed, whether the copy of
  its save began, whether the restore ran and succeeded, whether the state
  was frozen, and whether it arrived while the core was still starting up.
  `savinfo.py` decodes all of it.
- **Cartridge-load diagnostic (off in this build).** A diagnostic for the
  cartridge load path stays in the source, switched off (`NGPC_CART_DIAG`
  in `projects/ngpc_pocket.qsf`). Built with it, the core records in every
  Memory and sleep the checksum of the cartridge as the Pocket delivered
  it, and `tools/cartdiag.py` reads it. That is how the wrong checksum
  above was traced to inside the core, with the Pocket's delivery intact.
  Switched off, the source builds the release bitstream bit for bit.
- **Fit and timing.** The design sat at 99%, and rc4 no longer fit. The
  slow, non-critical blocks are now built for area, which brings it to
  {{ALM_PCT}}% ({{ALMS_USED}} of {{ALMS_TOTAL}} ALMs) with better timing than
  1.0.2 or the rc3 test build: −3.139 ns worst case on the main clock,
  against −3.169 ns for 1.0.2 and −3.386 ns for rc3. It still does not
  formally close timing. The build is fitter seed 7, picked from a 25-seed
  search.
- **Testing.** Several rounds of multi-agent code review, and a comparison
  with the MiSTer core's save and savestate code. Independent test benches
  written from a specification (save engine 32 + 38 scenarios, load path
  with the real bridge 26, savestate transport 10, copier, staging,
  settings gate 8, savinfo 87), each checked by mutation. Hardware testing
  on the Pocket: a full session on 1.1.0-rc5 (normal saves, refused and
  damaged files, sleep and wake, Memories, 1.0.x saves, Language, menu
  Reset, and the large saves of Unitron 2 and Faselei!), and on the release
  build itself, more than 50 quick quit-and-relaunch launches of Card
  Fighters' Clash without a wrong checksum, with a build known to show it
  reproducing it in the same session.

## Known limitations

- **Rarely, a game may start without its save, and nothing says so.**
  Whenever the core refuses a save file (a damaged file, an unknown format,
  another dump of the ROM, or the rare wrong checksum at launch described
  above), it keeps the file and saves nothing in that session. Quit and
  launch the game again; see
  [If a game starts without its save](#if-a-game-starts-without-its-save).
  To start over instead, move the file off the card first (and keep it).
- **A Memory that cannot rewind the save restarts the game.** The Pocket
  reports that the Memory could not be loaded, and the game starts over
  from the BIOS animation. (A Memory of a different game is simply turned
  away, and the game carries on.) This happens when the game has since saved something the
  Memory does not hold, typically a Memory made before the game had ever
  saved, loaded after a save exists. The core refuses the whole load rather
  than put the game back over a save it could not rewind. The save file
  stays as it was, unless the game was saving at that very moment: that
  save is cut short, as a reset would cut it. Continue from the game's own
  save, or load a more recent Memory. See
  [docs/KNOWN_BEHAVIORS.md](https://github.com/janisc/openfpga-NGPC/blob/main/docs/KNOWN_BEHAVIORS.md).
- **A short sound stutter when a Memory loads.** If the game is writing its
  save at that moment, the load waits for the write to finish. That wait is
  deliberate.
- **Menu Reset unloads the cartridge** and lands in the BIOS menu (MiSTer's
  keeps the game). Reset to BIOS is the intended way to get there. To
  restart a game, relaunch it. A menu Reset keeps your save.
- **The clock after sleep.** After waking from sleep, or loading a Memory,
  the NGP's clock carries on from the moment the state was taken, so it is
  behind by the time in between. Relaunching the game, or Reset to BIOS,
  sets it right.
- **Mono Palette has no effect with System = Mono**, because the mono BIOS
  has no palettes. (MiSTer hides the option in that case.)
- **Neo Turf Masters' in-game suspend** does not offer resume. The game
  keeps its suspend in the console's always-on memory, which starts empty
  at every launch. Sleep is the way to pause mid-round. See
  [docs/KNOWN_BEHAVIORS.md](https://github.com/janisc/openfpga-NGPC/blob/main/docs/KNOWN_BEHAVIORS.md).
- **Saves from the PR #5 test build (V3)** are not read. They stay on the
  card untouched.

## Reporting a problem

Please open an issue with:
- the game, and what happened just before (sleep, a Memory, Reset, a
  relaunch);
- your Pocket firmware version;
- the output of `python3 tools/savinfo.py "Saves/ngpc/common/Your Game.sav"`
  for the save in question, and the `.sav` itself if you can attach it;
- if a wake or a Memory load went wrong, or a game started without its
  save: a Memory made straight after it, before you quit, reset or load
  anything else. It records how that load ended, and the checksum the core
  worked out for the game.

If a save is still gone after a relaunch, copy these off the card before
you play again: the `.sav`, `System/user_sleepstate.sta` (if you haven't
slept since), and any Memories of that game in
`Memories/Save States/janisc.NGPC/`. A savestate carries a copy of the save
from the moment it was taken, so it may be possible to get the save back
from one. `savinfo.py` shows the save each one carries.

Saves and Memories from 1.0.x still load.
Built with Quartus Prime Lite 25.1.
